# Next.js App Router Fundamentals

## Summary
The App Router (`app/` directory) is the default and recommended routing system in Next.js 16.x (current stable: 16.3, September 2026). Folders define URL segments, special files (`page`, `layout`, `loading`, `error`, `not-found`, `route`, `default`, `template`) define UI and behavior, and every layout/page is a React Server Component by default. This skill covers file conventions, component hierarchy, dynamic segments, route groups, private folders, typed route helpers, and the async request APIs that are mandatory since v16.

## Category
Next.js

## Subcategories

## Problem It Solves
Teams (and AI agents trained on older data) mix Pages Router idioms (`getServerSideProps`, `next/router`, `_app.tsx`) with App Router code, access `params` synchronously, put shared UI in the wrong file, or create route conflicts. A clear mental model of how the file system maps to rendering boundaries prevents broken builds, lost layout state, and accidental client bundles.

## When To Use
- Starting any new Next.js project (App Router is the `create-next-app` default).
- Adding routes, layouts, loading/error boundaries, or dynamic segments.
- Organizing a growing `app/` tree (route groups, colocation, multiple root layouts).
- Reviewing agent-generated Next.js code for outdated conventions.

## When Not To Use
- Maintaining a Pages Router app that is not migrating (see [nextjs-pages-to-app-router-migration](../nextjs-pages-to-app-router-migration/Skill.md)).
- Client-only SPAs with no server rendering needs (see [vite-react-spa](../vite-react-spa/Skill.md)).
- Initial project scaffolding, tooling, and folder conventions beyond routing (see [react-nextjs-project-setup](../react-nextjs-project-setup/Skill.md)).
- Modal/slot routing details (see [nextjs-advanced-routing](../nextjs-advanced-routing/Skill.md)).

## Core Principles
1. **Folders are segments; files are behavior.** A route is only public when a `page.tsx` or `route.ts` exists in the folder.
2. **Server by default.** Layouts and pages are Server Components; add `'use client'` only at interactive leaves.
3. **Layouts persist, pages re-render.** Layouts do not re-render on client navigation between their children (partial rendering), so never rely on a layout for per-navigation checks.
4. **Request data is async.** `params`, `searchParams`, `cookies()`, `headers()`, `draftMode()` are Promises; synchronous access was removed in v16.
5. **One owner per URL.** `page.tsx` and `route.ts` cannot coexist in the same segment.
6. **Colocation is safe.** Non-special files inside `app/` are never routable.

## Best Practices
- Use the generated global helpers `PageProps<'/blog/[slug]'>`, `LayoutProps<'/dashboard'>`, and `RouteContext<'/api/users/[id]'>` (generated by `next dev`, `next build`, or `next typegen`) instead of hand-written param types.
- Keep the root layout minimal: `<html lang>`, `<body>`, fonts, global CSS, and deep-as-possible providers wrapping only `{children}`.
- Use route groups `(marketing)`, `(app)` to give sections different layouts without changing URLs.
- Use private folders `_components`, `_lib` for colocated non-route code to avoid future convention clashes.
- Add `not-found.tsx` and `error.tsx` at meaningful segment levels, plus `app/global-error.tsx` (must render its own `<html>`/`<body>`).
- Prefer `<Link>` from `next/link` for internal navigation (prefetching + client transitions); use `useRouter` from `next/navigation` (never `next/router` in `app/`).
- Keep `src/` or root layout consistent; `.env*` files always stay at the project root, even with `src/`.
- Add `data-scroll-behavior="smooth"` to `<html>` only if you need Next.js to override global smooth scrolling during navigation (v16 no longer does this by default).

## Implementation Guidance

### File conventions (render order, outer to inner)
| File | Purpose | Notes |
|---|---|---|
| `layout.tsx` | Shared, persistent UI | Root layout required; must render `<html>` and `<body>` |
| `template.tsx` | Like layout but remounts on navigation | Use for enter animations / per-page effects |
| `error.tsx` | Error boundary for the segment | Must be a Client Component |
| `loading.tsx` | Suspense boundary around `page` | Instant fallback, prefetchable |
| `not-found.tsx` | UI for `notFound()` | |
| `page.tsx` | Route UI | Makes segment public |
| `route.ts` | HTTP handler | Cannot coexist with `page.tsx` |
| `default.tsx` | Parallel-route fallback | Required for every slot in v16 |
| `global-error.tsx` | Root error boundary | Replaces root layout when active |

### Dynamic segments
| Folder | Matches | `params` type |
|---|---|---|
| `[slug]` | `/blog/a` | `{ slug: string }` |
| `[...slug]` | `/shop/a/b` | `{ slug: string[] }` |
| `[[...slug]]` | `/docs`, `/docs/a/b` | `{ slug?: string[] }` |

### Typical project tree
```txt
app/
├── (marketing)/
│   ├── layout.tsx          # marketing chrome
│   └── page.tsx            # "/"
├── (app)/
│   ├── layout.tsx          # authenticated chrome
│   ├── dashboard/
│   │   ├── loading.tsx
│   │   ├── error.tsx
│   │   └── page.tsx        # "/dashboard"
│   └── blog/[slug]/
│       ├── _components/PostBody.tsx
│       ├── not-found.tsx
│       └── page.tsx        # "/blog/:slug"
├── api/health/route.ts     # "/api/health"
├── layout.tsx              # root layout
├── global-error.tsx
├── sitemap.ts
└── robots.ts
proxy.ts                    # formerly middleware.ts (v16)
instrumentation.ts
next.config.ts
```

### Accessing params and searchParams (v16)
```tsx
// app/blog/[slug]/page.tsx
import { notFound } from 'next/navigation'
import { getPost } from '@/lib/posts'

export default async function Page(props: PageProps<'/blog/[slug]'>) {
  const { slug } = await props.params
  const { preview } = await props.searchParams
  const post = await getPost(slug)
  if (!post) notFound()
  return <article><h1>{post.title}</h1></article>
}
```

### Multiple root layouts
Remove `app/layout.tsx`, add a `layout.tsx` with `<html>`/`<body>` inside each top-level route group. Navigating between root layouts causes a full page load.

## Recommended Workflow
1. Scaffold with `npx create-next-app@latest` (App Router, TypeScript, Tailwind, ESLint flat config, AGENTS.md).
2. Sketch the URL map, then the layout nesting (which UI persists where).
3. Create route groups for sections needing distinct layouts.
4. Add `page.tsx` files; type them with `PageProps<'...'>`.
5. Add `loading.tsx`/`<Suspense>` and `error.tsx` where data is fetched.
6. Add `not-found.tsx`, `global-error.tsx`, metadata files.
7. Run `next typegen` / `next build` to validate types and conventions.

## Patterns
- **Section shell via route group:** `(dashboard)/layout.tsx` with sidebar; pages inside inherit it.
- **Colocated feature folder:** `app/orders/_components`, `app/orders/_lib/queries.ts`, `app/orders/page.tsx`.
- **Loading skeleton for one page only:** move `loading.tsx` + `page.tsx` into `(overview)/` group inside the segment.
- **Provider island:** `app/providers.tsx` (`'use client'`) wrapping `{children}` inside `<body>`.

## Anti-Patterns
- **`const { slug } = params` without await** — v16 removed sync access; types and runtime fail. Fix: `await props.params` (codemod `next-async-request-api`).
- **Importing `useRouter` from `next/router`** in `app/` — unsupported. Fix: `next/navigation` plus `usePathname`/`useSearchParams`/`useParams`.
- **Marking `layout.tsx` `'use client'`** to use one hook — ships the whole subtree's imports to the client. Fix: extract the interactive part into a small client component.
- **Auth check in layout only** — layouts don't re-run on sibling navigation and don't stop child segments from rendering. Fix: check in the Data Access Layer / page / action.
- **`page.tsx` and `route.ts` in the same folder** — build conflict. Fix: move the handler to `app/api/...`.
- **Calling your own Route Handler from a Server Component** — extra HTTP hop, fails at build. Fix: call the data function directly.

## Accessibility
- Always set `<html lang>` in the root layout (dynamic per locale when localized).
- Route changes are client transitions: ensure each page has a unique `<title>` (Metadata API) and a single `<h1>`; Next.js includes a route announcer, but verify focus lands sensibly (WCAG 2.4.3 Focus Order).
- `loading.tsx` fallbacks should not steal focus; use `aria-busy` on containers where appropriate.
- `not-found.tsx` and `error.tsx` must contain real headings and a link/button to recover (WCAG 3.3.x).

## Responsive Design
- Layouts are the right place for responsive shells (sidebar collapses to drawer); keep the toggle state in a small client component so the layout stays a Server Component.
- Avoid server-side device detection for layout decisions; use CSS/container queries so the static shell is shared.

## Performance
- Server Components add zero client JS; keep `'use client'` boundaries at leaves.
- Layout persistence means shared UI is not refetched on navigation.
- `loading.tsx` enables partial prefetching of dynamic routes; missing it on dynamic routes makes navigations feel blocked (see [nextjs-streaming-and-loading-ui](../nextjs-streaming-and-loading-ui/Skill.md)).

## Security
- Treat every `[param]` folder as untrusted user input; validate (zod) before querying.
- Colocated files are not routable, but anything imported into a Client Component is shipped to the browser. Use `import 'server-only'` in data modules.
- Do not rely on layouts or route groups as security boundaries.

## Testing
- Unit test synchronous Server/Client Components with Vitest + Testing Library; async Server Components are not supported by Vitest — cover them with Playwright E2E.
- E2E: verify 404s for invalid params, error boundaries render, and layouts persist state across navigation.
- `next build` in CI catches missing `default.tsx`, route conflicts, and type errors.

## Tooling
- `create-next-app` (generates AGENTS.md/CLAUDE.md), `next typegen`, `@next/codemod`.
- ESLint via `eslint-config-next` (flat config). `next lint` was removed in v16 — run `eslint` directly.
- Turbopack is the default bundler for dev and build (`--webpack` to opt out).
- Next.js DevTools MCP (`/_next/mcp`) for agents.

## Framework Notes
- Next.js 16 requires Node.js 20.9+, TypeScript 5.1+, React 19.2 (canary channel used by App Router).
- Pages Router still works and can coexist, but new features (Cache Components, `proxy.ts` patterns, root params) target the App Router.
- React (Vite SPA): there is no file-system router or server rendering; the closest equivalents are client routers with nested layouts. Choose Next.js when you need server rendering, streaming, SEO, or server-side data access (see [vite-react-spa](../vite-react-spa/Skill.md)).
- URL search-param state (filters, tabs) is best handled with nuqs on top of `useSearchParams` (see [react-url-state-nuqs](../react-url-state-nuqs/Skill.md)).

## AI Agent Guidance
- Read `node_modules/next/dist/docs/` (referenced by the generated AGENTS.md) before writing code; do not rely on pre-2025 training data.
- Do: await `params`/`searchParams`/`cookies()`/`headers()`; use `PageProps` helpers; import navigation hooks from `next/navigation`.
- Don't: generate `getServerSideProps`, `getStaticProps`, `_app.tsx`, `next/head`, or `middleware.ts` in new App Router code.
- Before declaring done: `next build` passes, `next typegen` types resolve, each new route has loading/error handling where it fetches, and no unnecessary `'use client'` at layout/page level.

## Examples
```tsx
// app/layout.tsx
import type { Metadata } from 'next'
import { Geist } from 'next/font/google'
import './globals.css'

const geist = Geist({ subsets: ['latin'] })

export const metadata: Metadata = {
  title: { template: '%s | Acme', default: 'Acme' },
  metadataBase: new URL('https://acme.com'),
}

export default function RootLayout({ children }: LayoutProps<'/'>) {
  return (
    <html lang="en" className={geist.className}>
      <body>{children}</body>
    </html>
  )
}
```

```tsx
// app/(app)/dashboard/error.tsx
'use client'
export default function ErrorPage({ error, retry }: { error: Error & { digest?: string }; retry: () => void }) {
  return (
    <div role="alert">
      <h2>Something went wrong</h2>
      <button onClick={() => retry()}>Try again</button>
    </div>
  )
}
```
